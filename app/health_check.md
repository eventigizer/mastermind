Run a read-only health check of this Windows machine and report what you find — a diagnosis, never a repair.

Rules
- Run read-only commands only. Change nothing anywhere: no process stopped, no setting changed, no file written — in this project or outside it.
- Read nothing under Claude's own config folder (`~/.claude`, or the folder `CLAUDE_CONFIG_DIR` names).
- Every change you would make is a recommendation: the exact command, what it fixes and what it costs. Mark each one that needs an elevated (administrator) shell, and mark every Defender exclusion as weakening the antivirus.
- Use PowerShell for the Windows reads (`Get-CimInstance`, `Get-WinEvent`, `Get-MpComputerStatus`); none of them needs elevation. Never start an elevated process — no `-Verb RunAs`, nothing that raises a UAC prompt.
- Never print a secret: a command line can carry a token, key or password — show it with that value replaced by `***`.
- Before printing anything from PowerShell, set `[Console]::OutputEncoding = [Text.UTF8Encoding]::new($false)` — piped output otherwise uses the console's old code page and garbles every non-ASCII character, a user folder's name among them.

1. Microsoft Defender
- Status: `Get-MpComputerStatus`, its `AMRunningMode` first. When the call fails or the mode reads anything but `Normal`, another antivirus does the scanning: name it (`Get-CimInstance -Namespace root/SecurityCenter2 -ClassName AntiVirusProduct`), say its scan cost is outside this check, and skip the rest of this section. Else: real-time protection, the last quick and full scan (an age of 4294967295 days means never), the signature age.
- Detections: events 1116 and 1117 in the `Microsoft-Windows-Windows Defender/Operational` log.
- Scan cost on development folders: whether an exclusion covers the folder holding the code checkouts, Claude's config folder, Node's install folder and Python's install folder. A standard shell cannot list the exclusions — read event 5007 in the same log, from each event's `Old Value` / `New Value` data fields (`([xml]$e.ToXml()).Event.EventData.Data`), never its message text, whose labels follow the display language. An exclusion covers a folder when the newest 5007 naming that folder, or a folder above it, as `Exclusions\Paths\<path>` has it under `New Value`; under `Old Value` alone it was removed. Three rules narrow that: a path through a user variable (`%USERPROFILE%`, `%APPDATA%`, `%LOCALAPPDATA%`, `%TEMP%`) resolves under the system account and covers none of the user's folders; a subfolder that is a symlink or junction (nvm's `nodejs` link, for one) is covered only by its own entry, and one made after Defender started counts only after a restart; a `*` matches exactly one folder level. With none found, say the answer is unknown, since the log rolls over.
- For the code checkouts, recommend a Dev Drive first (Windows 11 — Settings → System → Storage → Advanced storage settings → Disks & volumes; it needs administrator rights and a new volume of 50 GB or more, since an existing volume cannot be converted and C: cannot be one): Defender keeps scanning it in performance mode, opening files first and scanning after, which protects far better than an exclusion; whether a drive already is one needs an elevated `fsutil devdrv query <drive>:`. A folder exclusion is the fallback — never a process exclusion, which skips every file that process opens, anywhere.
- For an elevated shell, recommend confirming with `(Get-MpPreference).ExclusionPath`, and measuring where the scan time goes: `New-MpPerformanceRecording -RecordTo $env:TEMP\defender.etl -Seconds 120` during normal work, then `Get-MpPerformanceReport -Path $env:TEMP\defender.etl -TopProcesses 10 -TopPaths 10 -TopExtensions 10`, then `Remove-Item $env:TEMP\defender.etl` — the recording never lands in this project.

2. Memory and CPU
- The machine: total and free memory and the commit charge (`Win32_OperatingSystem`); how busy the CPU is, sampled a few times over a few seconds (`Win32_PerfFormattedData_PerfOS_Processor`, the `_Total` row).
- The top processes by private memory, and by CPU over the same few seconds (`Win32_PerfFormattedData_PerfProc_Process` — a `PercentProcessorTime` over 100 means more than one core; Defender's own CPU reads only this way without elevation). In both, discard the first sample, which often reads 0, and match a process's samples by `IDProcess`, never by `Name`, whose `Code#3`-style numbering shifts as processes come and go. These classes read the same in every Windows display language; a performance-counter path typed by name does not.
- VS Code: name each `Code.exe` — or a look-alike's own exe (`Code - Insiders.exe`, `Cursor.exe`, `VSCodium.exe`, `Windsurf.exe`) — by its role from its command line — a renderer (`--type=renderer`; a Claude panel's memory lives in one); a `--utility-sub-type=node.mojom.NodeService` process, which is a window's extension host when language servers and `claude.exe` run under it, else VS Code's terminal host or one of its own services; each language server, a child of an extension host, by the script or exe on its command line (`tsserver.js`, `eslintServer.js`, `Microsoft.CodeAnalysis.LanguageServer.exe`, …) — each with its private memory.
- A Claude panel's memory cannot be told apart from a renderer's command line. When a renderer is large, point at Mastermind's VS Code health item: with VS Code's debug port on it reads each Claude panel's heap, and a click on it reloads that window's panels once no session there is working — which restarts every Claude session in the window, each resuming from its transcript.

3. Leftover processes
- A leak is a process whose owner is gone and that nothing will end. Plenty of processes have no live parent by design — name them and set them aside:
  - build servers that outlive their build and exit once idle: MSBuild's reusable worker nodes (`/nodemode:` and `/nodeReuse:true` on the command line, under `MSBuild.exe` or `dotnet`), the C# compiler server (`VBCSCompiler` anywhere on the command line — its own exe, or `dotnet … VBCSCompiler.dll`), Gradle and Kotlin daemons;
  - an application's own helpers, and its main process restarted by its own launcher (a browser, a VPN or sync client);
  - the members of a Git Bash pipeline (`tail`, `grep`, `sed`, …), whose Windows parent is already gone while their Git Bash parent lives. Judge these from Git Bash: a process whose `/proc/<pid>/ppid` names a pid with no `/proc` entry is orphaned — never judge it by its Windows parent. A ppid of 1 means top-level or orphaned — Git Bash hands an orphan to pid 1, and no `/proc/1` exists: judge that one by its Windows parent (`/proc/<pid>/winpid`, then `Win32_Process`), owned only while that parent is alive and was created before it, since Windows reuses pids.
- Give every process its age. One a few seconds old is a tool call or a hook in flight, not a leak.
- Claude sessions: a VS Code window's `claude.exe` processes run under its extension host — its children, or further down when a launcher wrapper starts them, so count them anywhere beneath it; one carrying `--claude-in-chrome-mcp` is the Chrome-integration server, not a session. Report how many sessions run under each window, so they can be set against the sessions the user has open: a session archived in VS Code keeps its `claude.exe` running until its window closes — point at Mastermind's `Reap background agents`, which stops archived idle sessions and spares working ones.
- Everything else with no live owner: its age, memory, command line (secrets masked) and why it looks orphaned.

4. The report
- Worst first. Each finding: what it is, the evidence (the numbers, the event), and the exact command recommended, marked where it needs elevation.
- End with one line on what looked healthy.
- Run none of the recommended commands.
